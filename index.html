A support agent, taken apart.

Memory, tool-calling and retrieval, written in pure Python with no agent framework — to find out exactly where the model stops and the code has to start.

Stack FastAPI · Groq (Llama 3.3 70B) · sentence-transformers · NumPy Code github.com/VETERAN1945/python-ai-agent-support

Why

The same agent already worked. I couldn't see inside it.

I had built this affiliate-support agent in n8n, where every layer sits behind a node: the tool call, the memory, the retrieval. It answered, the answers looked convincing, and that was all I could observe.

So I rebuilt it from nothing in Python — one layer at a time, printing every intermediate value to the terminal. Two failures showed up that had been invisible in the visual builder. Both are below.

Finding 01

Retrieval that returns a confident wrong answer

Documents are matched by embedding distance: the question becomes a 384-dimension vector, so does every document, and NumPy measures which is closest. With all-MiniLM-L6-v2 the three documents landed on top of each other — the all in its name means all English datasets, and the knowledge base is in Russian.

Nothing failed. No exception, no warning, no empty result. The agent picked a document and answered from it — by coin flip.

all-MiniLM-L6-v2 · English-onlyselection by noise
docs a, b, c — indistinguishable

Spread between first and second place: 0.005. The winner is whichever way the noise fell.

paraphrase-multilingual-MiniLM-L12-v2clear winner
3.605 · a
4.724 · c
4.750 · b

Question: “How much do you pay partners?” — gap to second place 1.12. Across the test set, gaps ran 0.63–1.24.

Absolute distances aren't comparable between models — the vector scales differ. The gap inside a single run is the thing that means something, and it is the number worth printing.

Finding 02

Search the user's question, not the model's paraphrase of it

The model decides which tool to call and fills in its arguments. For the search tool it often compressed a whole question down to one word — “partners”. A single word gives a vector with almost no direction: near-equally close to every document.

The fix was one line. The numbers the model invents for a multiply tool can't come from anywhere else, so those stay. But the text of the question I already have, clean and unmodified.

if tool_name == "multiply":
    result = multiply(**args)          # only the model has these numbers
else:
    result = search_docs(q.message)    # was: search_docs(**args)

Same question, different document retrieved — the right one. The rule that came out of it: take back from the model everything you can obtain yourself; leave it only what you can't.

Anything that has to be exact was moved out of the model and into code. The model is left with the part where exactness isn't required.

Failure handling

A crash must not poison the next request

Groq regularly emits a malformed tool call — 400 tool_use_failed, three times across five requests in one run. Catching it and returning “something went wrong” isn't enough: the session now holds a tool request with no matching result, and the next message from that user breaks on the corrupted history.

So the length of the history is recorded before the work starts, and everything written past that mark is deleted in the except. A savepoint and a rollback, in the SQL sense. The try/except saves the current request; the rollback saves every future one.

snapshot = len(history)      # after appending the user message
...
except Exception as e:
    del history[snapshot:]   # nothing orphaned survives

Verified against four real failures — one expired key, three malformed tool calls. Every session came back holding exactly the user message and the reply.

This class of bug doesn't exist in a visual builder: there the workflow dies together with its data. It appears the moment state outlives the call.

Known gaps

What isn't here, on purpose

A learning project, a long way from production. The honest list:

  • No system prompt.Found on the final run: retrieval returned the correct document — multi-accounting is banned — and the model answered the opposite, straight from its weights. Nothing in the code makes the document authoritative. Next step.
  • No relevance cut-off.The nearest document is always returned, however far away everything is. It needs to be able to say it found nothing.
  • No retry on malformed tool calls.A frequent error that a repeated request usually clears.
  • Sessions live in process memory.A restart wipes every conversation.
  • Documents are hard-coded, and there is no auth.Changing a document means editing the code and restarting. Any caller can send someone else's user_id and read their history.
  • History grows without limit.It will reach the token ceiling eventually.

What the project actually taught, beyond the code: the more an error costs, the less freedom the model gets. Cheap questions can be phrased by the model. Money, bans and deadlines should come as text from code. Very expensive cases shouldn't reach a bot at all.
