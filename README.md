# AI-агент на чистом Python

Support-бот партнёрской программы: LLM + память + tool-calling + RAG, написанный
без агентных фреймворков (LangChain, LlamaIndex и т.п.).

Цель проекта учебная — разобрать механику агента изнутри. Тот же агент у меня
собран в n8n, но там всё скрыто за нодами. Здесь каждый слой написан руками,
чтобы видеть, где заканчивается модель и начинается код.

## Что внутри

- **Вызов LLM** — Groq, `llama-3.3-70b-versatile`
- **Память** — истории диалогов в словаре `sessions`, ключ `user_id`
- **Tool-calling** — два инструмента: `multiply` и `search_docs`
- **RAG** — эмбеддинги `paraphrase-multilingual-MiniLM-L12-v2`, поиск ближайшего
  документа по евклидову расстоянию (`numpy`), без векторной БД
- **HTTP-слой** — FastAPI + uvicorn, эндпоинт `POST /chat`
- **Обработка сбоев** — `try/except` вокруг обоих вызовов модели плюс откат
  истории диалога при ошибке

## Файлы

| Файл | Что это |
|---|---|
| `api.py` | Финальная версия — FastAPI-сервер, все слои вместе |
| `first_call.py` | Консольная версия, ранний этап: тот же агент в цикле `while True` |
| `test_call.py` | Черновик: отдельные вызовы API, на которых проверялись куски перед сборкой |

Ранние версии оставлены намеренно: по ним видно, как проект собирался по слоям
и что изменилось при переезде из консоли в веб.

## Запуск

```bash
pip install -r requirements.txt
```

Создать `.env` в корне проекта:

```
GROQ_API_KEY=gsk_...
```

Ключ — на console.groq.com/keys.

```bash
python -m uvicorn api:app --reload
```

Первый старт долгий: скачивается модель эмбеддингов (~500 МБ).
Дальше — http://127.0.0.1:8000/docs

Тело запроса:

```json
{"user_id": "u1", "message": "Сколько вы платите партнёрам?"}
```

## Откат истории при сбое

Groq регулярно генерирует битый вызов инструмента (`400 tool_use_failed`).
Если поймать ошибку и просто вернуть пользователю «произошла ошибка», в истории
диалога останется заявка на вызов инструмента без ответа на неё — и следующий
запрос этого пользователя упадёт уже на испорченной истории.

Поэтому перед работой запоминается длина истории, а в `except` всё, что успело
дописаться после этой отметки, удаляется. По сути — откат транзакции: `snapshot`
это точка сохранения, `del history[snapshot:]` — сам откат. `try/except` спасает
текущий запрос, откат — все будущие запросы этого пользователя.

## Две вещи, найденные в бою

**1. Многоязычность эмбеддингов — не деталь, а условие работы.**
На `all-MiniLM-L6-v2` (`all` = all *English* datasets) русские документы дают
слипшиеся векторы: разрыв между первым и вторым местом — 0.005, то есть выбор
по шуму. Ошибок в логах при этом нет, ответ приходит, ответ неверный. После
перехода на многоязычную модель разрывы стали 0.63–1.24.

**2. Искать надо по вопросу пользователя, а не по формулировке модели.**
Изначально в `search_docs` уходил аргумент, который придумала модель, — часто
одно слово («партнёрам»). Одно слово даёт вектор почти без направления,
одинаково близкий ко всем документам. После замены на исходный текст вопроса
тот же запрос стал находить другой — правильный — документ.

Общий вывод: всё, что должно быть точным, выносится из модели в код. Модели
остаётся понять смысл и сформулировать текст — там точность не нужна.

## Чего здесь нет (осознанно)

Проект учебный, до продакшена ему далеко. Известные дыры:

- **Нет `system`-промпта.** Найдено на финальном прогоне: поиск отдал верный
  документ («мультиаккаунты банятся»), а модель ответила наоборот — взяла ответ
  из своих весов. В коде нет ни одной строки, обязывающей отвечать по документу.
  Следующий шаг.
- **Нет порога отсечки в поиске** — всегда возвращается ближайший документ,
  даже если все далеко. Нужен ответ «не нашёл».
- **Нет ретрая на `tool_use_failed`** — ошибка частая, лечится повтором запроса.
- **Сессии живут в памяти процесса** — рестарт стирает все диалоги.
- Документы захардкожены в коде, авторизации нет, история растёт без ограничения
  и рано или поздно упрётся в лимит токенов.
